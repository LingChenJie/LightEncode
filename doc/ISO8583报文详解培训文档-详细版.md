# ISO 8583 报文详解培训文档

> 面向 POS 开发、测试、技术支持及刚接触银行卡支付系统的新人

## 1. 文档说明

本文档是《ISO 8583 报文详解培训》PPT 的详细讲义版本。PPT 用于课堂展示，本讲义用于课前预习、课后复习和项目对接时查阅。

建议培训时间为 60～90 分钟。完成培训后，学员应该能够：

- 说明为什么银行卡交易需要统一的报文规范。
- 区分 ISO 8583 报文、渠道封装和网络传输协议。
- 解释 MTI、Bitmap 和 Data Elements 的作用。
- 根据 Bitmap 判断报文中存在哪些数据域。
- 区分 FIX、LLVAR、LLLVAR 以及 ASCII、BCD、Binary、HEX。
- 根据字段规范完成基础组包和解包。
- 初步定位字段错位、金额错误、乱码和 MAC 校验失败等问题。

本文档主要讲解支付行业中常见的传统 ISO 8583 实现方式，尤其是常见的 1987 风格报文。不同版本、银联规范、收单机构和支付平台可能有不同实现，以下示例不能代替实际接口文档。

## 2. 为什么需要 ISO 8583

### 2.1 一笔银行卡交易涉及多个参与方

一笔常见的 POS 消费交易，可能经过以下系统：

```text
POS 终端
   ↓
收单机构 / 支付平台
   ↓
卡组织 / 交换网络
   ↓
发卡行
```

发卡行处理完成后，响应报文沿相反方向返回 POS 终端。

这些系统可能由不同公司开发，使用不同语言、操作系统和网络架构。如果没有共同约定，同一段交易数据可能产生大量歧义：

- 哪个字段表示银行卡号？
- 金额的单位是元还是分？
- 字段是固定长度还是变长？
- 长度值是 ASCII、BCD 还是二进制？
- 某个字段不存在时，接收方如何知道？
- 成功、拒绝、超时分别如何表达？
- 如何确认响应属于原来的那笔请求？

ISO 8583 的核心价值，就是为银行卡交易消息建立一套共同表达框架。

### 2.2 ISO 8583 解决了什么问题

可以把 ISO 8583 理解成金融交易消息的“语法框架”：

- MTI 说明这是什么类型的消息。
- Bitmap 说明消息中有哪些数据域。
- Data Elements 承载金额、流水号、终端号等业务数据。
- 字段定义说明每个数据域的长度、格式和编码规则。

ISO 官方将其描述为收单方与发卡方之间交换金融交易卡消息的共同接口，并明确传输方式和结算方式不属于该标准的范围。

## 3. ISO 8583 是什么，又不是什么

### 3.1 ISO 8583 是什么

可以使用下面这句话作为统一定义：

> ISO 8583 是面向金融交易卡消息交换的通用接口标准，用于约定消息结构、格式和数据表达方式，使收单方、交换网络和发卡方能够按照共同规则理解一笔交易。

常见应用场景包括：

- 授权和预授权。
- 消费、取现和转账。
- 撤销和退货。
- 冲正和交易通知。
- 余额查询。
- 签到、签退及网络管理。
- 对账和批结算。

具体是否使用这些消息、使用哪个 MTI、携带哪些数据域，由实际渠道规范决定。

### 3.2 ISO 8583 不是什么

ISO 8583 不是以下内容：

- 不是 TCP、HTTP、HTTPS 等网络传输协议。
- 不是所有支付机构完全相同的一串固定字节。
- 不是终端和后台之间完整的连接管理方案。
- 不单独规定全部密钥管理、加密和 MAC 规则。
- 不单独规定所有清算、结算和差错处理流程。
- 不保证不同机构对每个数据域的定义完全相同。

因此，开发一个真实支付项目至少需要同时理解以下几类规范：

| 规范层次 | 需要解决的问题 |
|---|---|
| ISO 8583 基础模型 | 报文如何组织、字段如何描述 |
| 银联或卡组织规范 | 某个支付网络如何使用 ISO 8583 |
| 收单机构接口规范 | 具体交易携带哪些域、编码和码值是什么 |
| 安全规范 | 密钥、PIN、MAC、敏感数据如何处理 |
| 通信规范 | 长连接、超时、报文长度、粘包和重连如何处理 |

## 4. 报文的分层结构

### 4.1 传统 ISO 8583 核心结构

在常见的 1987 风格实现中，ISO 8583 核心报文可以表示为：

```text
[MTI] [Bitmap(s)] [Data Elements]
```

- MTI：Message Type Indicator，消息类型指示符。
- Bitmap：位图，表示哪些数据域存在。
- Data Elements：数据域，承载实际业务数据。

### 4.2 渠道封装不是 ISO 核心结构

很多实际渠道会在 ISO 8583 核心报文外增加封装：

```text
[Length] [TPDU] [Header] [MTI] [Bitmap] [Data Elements]
└───────渠道自定义───────┘ └──────ISO 8583 核心──────┘
```

常见作用如下：

| 部分 | 常见作用 | 是否固定存在 |
|---|---|---|
| Length | 表示后续报文长度，帮助解决分包和粘包 | 否 |
| TPDU | 终端、网络或路由信息 | 否 |
| Header | 版本、机构、交易路由等自定义信息 | 否 |
| MTI | 描述消息类型 | 常见 ISO 核心组成 |
| Bitmap | 描述数据域存在性 | 常见 ISO 核心组成 |
| Data Elements | 承载业务字段 | 常见 ISO 核心组成 |

不能把某个项目中的 Length、TPDU、Header 长度直接当成 ISO 8583 的统一规定。

### 4.3 MAC 通常是一个数据域

MAC 并不一定是报文末尾独立存在的固定结构。在很多传统实现中：

- DE64 用于 64 位 MAC。
- DE128 用于扩展报文中的 MAC。

是否携带 MAC、放在 DE64 还是 DE128，以及算法、密钥、计算范围和补位方式，都必须查看渠道安全规范。

## 5. MTI：消息类型指示符

### 5.1 MTI 的基本作用

MTI 通常由 4 位数字组成，用于描述消息的基本性质。

以常见 ISO 8583:1987 风格中的 `0200` 为例：

```text
0 | 2 | 0 | 0
│   │   │   └─ 消息发起方
│   │   └───── 消息功能
│   └───────── 消息类别
└───────────── 版本
```

| 位置 | 常见含义 | `0200` 示例 |
|---|---|---|
| 第1位 | ISO 8583 版本 | `0` 常表示 1987 版风格 |
| 第2位 | 消息类别 | `2` 表示金融交易类 |
| 第3位 | 消息功能 | `0` 表示请求 |
| 第4位 | 消息发起方 | `0` 常表示收单方发起 |

注意：MTI 不表示“处理优先级”。不同 ISO 8583 版本和不同渠道对具体数字的解释可能不同。

### 5.2 常见 MTI 组合

| 请求 | 响应 | 常见用途 |
|---|---|---|
| 0100 | 0110 | 授权请求与授权响应 |
| 0200 | 0210 | 金融交易请求与响应 |
| 0220 | 0230 | 金融通知与通知响应 |
| 0400 | 0410 | 冲正请求与冲正响应 |
| 0500 | 0510 | 对账或结算类请求与响应，具体看规范 |
| 0800 | 0810 | 网络管理请求与响应 |

### 5.3 冲正不等于撤销

新人经常把冲正和撤销混为一谈。

- 撤销通常是业务主动发起，目的是取消原交易。
- 冲正常用于通信超时、响应丢失或交易状态不确定等异常场景。
- 冲正的目的是避免终端和主机对交易状态理解不一致。

例如，POS 已经把消费请求发送给后台，后台可能已经扣款，但响应在网络中丢失。POS 不知道交易是否成功，此时可能需要查询或冲正，而不能简单把交易当成失败。

## 6. Bitmap：数据域存在性索引

### 6.1 Bitmap 的作用

Bitmap 不是业务数据，而是一张“字段目录”。它告诉解析器：

> 接下来应该按照什么顺序读取哪些数据域。

传统主位图长度为 64 bit，也就是 8 bytes。

- bit 1：第二位图存在标志。
- bit 2～64：对应 DE2～DE64。
- bit 1 为 `0`：没有第二位图。
- bit 1 为 `1`：主位图后还有 8 bytes 第二位图。
- 第二位图描述 DE65～DE128。

特别注意：主位图 bit 1 不是普通数据域标志。

### 6.2 DE64 和 DE128 如何判断

- DE64 是否存在，由主位图 bit 64 决定。
- DE128 是否存在，由整个 128 位 Bitmap 的 bit 128 决定。
- 主位图 bit 1 只说明第二位图是否存在，不能用来判断 DE64。

### 6.3 Bitmap 的传输形式

Bitmap 可以采用不同传输方式：

| 形式 | 主位图长度 | 示例特点 |
|---|---:|---|
| Binary | 8 bytes | 每个 bit 直接存放在字节中 |
| ASCII HEX | 16 bytes | 每个原始字节使用两个 HEX 字符表示 |

例如，原始 Binary Bitmap：

```text
30 20 04 00 00 C0 80 01
```

如果以 ASCII HEX 传输，会变成字符：

```text
"3020040000C08001"
```

两者看起来相同，但字节数不同：前者 8 bytes，后者 16 bytes。

### 6.4 Bitmap 手算示例

假设报文包含以下字段：

```text
DE3、DE4、DE11、DE22、DE41、DE42、DE49、DE64
```

将 64 bit 分成 8 个字节：

| 字节 | 对应 bit | 存在的数据域 | Binary | HEX |
|---|---|---|---|---|
| B1 | 1～8 | DE3、DE4 | 0011 0000 | 30 |
| B2 | 9～16 | DE11 | 0010 0000 | 20 |
| B3 | 17～24 | DE22 | 0000 0100 | 04 |
| B4 | 25～32 | 无 | 0000 0000 | 00 |
| B5 | 33～40 | 无 | 0000 0000 | 00 |
| B6 | 41～48 | DE41、DE42 | 1100 0000 | C0 |
| B7 | 49～56 | DE49 | 1000 0000 | 80 |
| B8 | 57～64 | DE64 | 0000 0001 | 01 |

最终得到：

```text
Bitmap HEX = 3020040000C08001
```

### 6.5 第一个字节的理解

第一个字节为 `0x30`：

```text
HEX     30
Binary  0011 0000
bit     1234 5678
```

- bit 1 为 0：没有第二位图。
- bit 2 为 0：DE2 不存在。
- bit 3 为 1：DE3 存在。
- bit 4 为 1：DE4 存在。

## 7. 常见数据域

下面的定义是传统支付报文中的常见用法，不代表所有机构完全一致。

### 7.1 交易和账户字段

| 数据域 | 常见名称 | 常见作用 | 常见格式示例 |
|---|---|---|---|
| DE2 | Primary Account Number | 主账号或卡号 | LLVAR，最长常见为19位数字 |
| DE3 | Processing Code | 处理码，描述交易处理类型 | 常见为6位数字 |
| DE4 | Amount, Transaction | 交易金额 | 常见为12位数字 |
| DE11 | Systems Trace Audit Number | 系统跟踪号 STAN | 常见为6位数字 |
| DE12 | Time, Local Transaction | 本地交易时间 | 常见为 hhmmss |
| DE13 | Date, Local Transaction | 本地交易日期 | 常见为 MMDD |
| DE22 | Point of Service Entry Mode | 服务点输入方式码 | 常见为3位数字 |

#### DE2 主账号

DE2 通常承载卡号或账户标识。需要注意：

- 报文传输是否加密或保护，以安全规范为准。
- 页面、日志和监控中不得完整展示真实卡号。
- “日志脱敏”不能理解成“报文传输一定掩码”。

#### DE3 处理码

DE3 不是金额。它通常用于描述交易处理类型，例如消费、查询或其他账户处理方式。

同一个 MTI 可能结合不同 DE3 表示不同具体交易，因此不能只看 MTI 判断全部业务含义。

#### DE4 交易金额

DE4 通常是金额字段。常见规则包括：

- 固定长度数字。
- 不带小数点。
- 按币种最小单位表达。
- 人民币场景经常以“分”为单位。

例如：

```text
DE4 = 000000001000
```

如果接口规定单位为分，则表示：

```text
1000 分 = 10.00 元
```

不能脱离接口规范直接假设所有金额都以分为单位。

#### DE11 系统跟踪号

DE11 常用于：

- 请求与响应关联。
- 日志检索。
- 交易链路跟踪。
- 配合其他字段定位原交易。

DE11 可能循环使用，不应描述成永不重复的全局唯一标识。

### 7.2 终端、商户和结果字段

| 数据域 | 常见名称 | 常见作用 |
|---|---|---|
| DE37 | Retrieval Reference Number | 交易检索和关联 |
| DE39 | Response Code | 主机处理结果码 |
| DE41 | Card Acceptor Terminal Identification | 终端标识 |
| DE42 | Card Acceptor Identification Code | 商户或受卡方标识 |
| DE49 | Currency Code, Transaction | 交易货币代码 |

`156` 常用于人民币货币代码，但字段内容、长度和编码仍应查看接口规范。

### 7.3 安全和介质字段

| 数据域 | 常见用途 | 注意事项 |
|---|---|---|
| DE52 | PIN Data | 通常为 Binary，不得作为普通文本处理 |
| DE55 | ICC / EMV Data | 常承载 EMV TLV 数据，编码和长度依渠道而定 |
| DE64 | Message Authentication Code | 常用于主位图范围内的 MAC |
| DE128 | Message Authentication Code | 常用于包含第二位图的报文 MAC |

## 8. 定长域和变长域

### 8.1 FIX 固定长度

固定长度字段不携带长度指示符，接收方直接按字段定义读取指定长度。

假设某渠道定义：

```text
DE41 = ans8
```

则解包时读取 8 个字符或 8 个约定单位。具体如何补位、左对齐还是右对齐，需要查看字段定义。

### 8.2 LLVAR

LLVAR 表示字段前面有“两位十进制长度指示符”。

概念结构：

```text
[两位长度] [实际数据]
```

常见情况下可表达 `00～99` 的长度，但长度单位可能是：

- 数字位数。
- 字符数。
- 字节数。

### 8.3 LLLVAR

LLLVAR 表示字段前面有“三位十进制长度指示符”。

```text
[三位长度] [实际数据]
```

常见情况下可表达 `000～999` 的长度单位。

### 8.4 “两位长度”不等于“两字节长度”

假设 PAN 为：

```text
6222021234567890
```

长度是 16 位数字。

#### ASCII 长度头

```text
字符："16"
HEX：31 36
占用：2 bytes
```

如果 PAN 本身也使用 ASCII：

```text
长度头 2 bytes + 数据 16 bytes = 18 bytes
```

#### Packed BCD 长度头

```text
十进制长度：16
BCD HEX：16
占用：通常 1 byte
```

如果 PAN 本身使用 Packed BCD：

```text
长度头 1 byte + 数据 8 bytes = 9 bytes
```

因此，下面的表述不严谨：

```text
LLVAR = 双字节变长
LLLVAR = 三字节变长
```

推荐表述：

```text
LLVAR = 两位十进制长度指示符
LLLVAR = 三位十进制长度指示符
```

## 9. ASCII 编码

### 9.1 基本概念

ASCII 是字符编码。常见数字字符对应关系：

| 字符 | 十进制 | HEX | Binary |
|---|---:|---|---|
| `0` | 48 | 30 | 0011 0000 |
| `1` | 49 | 31 | 0011 0001 |
| `2` | 50 | 32 | 0011 0010 |
| `9` | 57 | 39 | 0011 1001 |

### 9.2 MTI `0200` 的 ASCII 表示

```text
字符       0    2    0    0
十进制    48   50   48   48
HEX       30   32   30   30
```

实际字节：

```text
30 32 30 30
```

总长度为 4 bytes。

### 9.3 ASCII 和 HEX 不要混淆

`30` 可能有两种完全不同的含义：

1. 一个原始字节 `0x30`，占 1 byte。
2. 文本字符串 `"30"`，实际是 `0x33 0x30`，占 2 bytes。

调试日志经常以 HEX 展示字节，因此“日志里看到 30”不代表网络中发送的是字符 `3` 和字符 `0`。

## 10. 8421 BCD 编码

### 10.1 什么是 8421 BCD

8421 BCD 对每一位十进制数字分别编码，每位数字使用 4 bit，权值依次为 8、4、2、1。

| 十进制 | 8421 BCD | 权值计算 |
|---:|---|---|
| 0 | 0000 | 0 |
| 1 | 0001 | 1 |
| 2 | 0010 | 2 |
| 3 | 0011 | 2 + 1 |
| 4 | 0100 | 4 |
| 5 | 0101 | 4 + 1 |
| 6 | 0110 | 4 + 2 |
| 7 | 0111 | 4 + 2 + 1 |
| 8 | 1000 | 8 |
| 9 | 1001 | 8 + 1 |

BCD 不是把整个十进制数直接转换成普通二进制，而是逐位编码。

### 10.2 Packed BCD

两个十进制数字各占 4 bit，可以组合成 1 byte。

数字串 `0200`：

```text
0      2      0      0
0000   0010   0000   0000
└──02──┘      └──00──┘
```

最终结果：

```text
02 00
```

占用 2 bytes。相同字符串使用 ASCII 时需要 4 bytes。

### 10.3 奇数位数字如何补位

假设数字串为：

```text
12345
```

常见处理方式可能包括：

```text
左侧补 0：01 23 45
右侧补 0：12 34 50
右侧补 F：12 34 5F
```

补在高位还是低位、补 `0` 还是 `F`，没有脱离字段规范的统一答案。

## 11. Binary 与 HEX

### 11.1 Binary 字段

Binary 字段表示其值按原始字节解释，而不是按字符文本解释。

常见 Binary 数据包括：

- Bitmap。
- PIN Block。
- MAC。
- 加密结果。
- 部分 EMV 数据。

ASCII 和 BCD 最终也会变成字节，因此“Binary 是没有编码的字节”并不严谨。更准确的说法是：

> Binary 字段的值直接按字节含义解释，不先转换成字符文本。

### 11.2 HEX 是显示方式

一个字节由 8 bit 组成，通常用两个 HEX 字符表示。

```text
Binary：0011 0000
HEX：30
```

`HEX 30` 是对一个字节值的显示。如果把它转换成文本 `"30"` 再发送，实际字节会变成：

```text
33 30
```

长度从 1 byte 变成 2 bytes。

## 12. 0200 消费请求示例

下面用一笔教学用消费请求贯穿组包过程。所有数据均为虚构值。

### 12.1 字段清单

| 项目 | 示例值 | 说明 |
|---|---|---|
| MTI | `0200` | 金融交易请求 |
| DE3 | `000000` | 处理码示例 |
| DE4 | `000000001000` | 金额示例，若单位为分则为10.00元 |
| DE11 | `123456` | 系统跟踪号 |
| DE22 | `051` | 输入方式码示例，具体含义查渠道码表 |
| DE41 | `SUNMI001` | 终端标识示例 |
| DE42 | `123456789012345` | 受卡方标识示例 |
| DE49 | `156` | 人民币代码示例 |
| DE64 | `A1B2C3D4E5F60708` | 8 bytes MAC 展示值，不是真实计算结果 |

### 12.2 计算 Bitmap

数据域集合：

```text
3、4、11、22、41、42、49、64
```

Bitmap：

```text
3020040000C08001
```

### 12.3 逻辑报文结构

```text
[0200]
[3020040000C08001]
[DE3]
[DE4]
[DE11]
[DE22]
[DE41]
[DE42]
[DE49]
[DE64]
```

字段必须按照域号从小到大排列。

### 12.4 逻辑报文示例

为便于阅读，下面使用分隔符展示。真实报文通常不会包含这些竖线和字段名称。

```text
0200
| 3020040000C08001
| 000000
| 000000001000
| 123456
| 051
| SUNMI001
| 123456789012345
| 156
| A1B2C3D4E5F60708
```

真实字节流还取决于以下定义：

- MTI 是 ASCII 还是 BCD。
- Bitmap 是 8 bytes Binary 还是 16 字符 ASCII HEX。
- 每个字段是 ASCII、BCD 还是 Binary。
- DE64 是原始 8 bytes 还是 16 字符 HEX。
- 是否存在 Length、TPDU 和 Header。

因此，仅凭上面的逻辑报文不能直接确定最终网络字节流。

## 13. 组包流程

### 13.1 业务组装阶段

1. 确定交易场景，例如消费、查询或冲正。
2. 选择 MTI。
3. 根据渠道规范准备必选域和条件域。
4. 校验金额单位、处理码、输入方式码等业务值。
5. 根据实际字段集合生成 Bitmap。

### 13.2 字节编码阶段

1. 按 FIX、LLVAR、LLLVAR 处理字段边界。
2. 根据字段定义执行 ASCII、BCD 或 Binary 编码。
3. 按域号从小到大写入字段。
4. 如果需要，按约定规则计算 MAC。
5. 如果需要，添加 Length、TPDU 和 Header。
6. 将最终字节流交给通信层发送。

### 13.3 组包伪代码

```text
fields = {}
fields[3]  = "000000"
fields[4]  = "000000001000"
fields[11] = "123456"
fields[22] = "051"
fields[41] = "SUNMI001"
fields[42] = "123456789012345"
fields[49] = "156"

validate(fields, channelFieldDefinitions)

bitmap = buildBitmap(fields.keys + DE64)

bodyWithoutMac = encode(MTI)
               + encode(bitmap)
               + encodeFieldsInAscendingOrder(fields)

mac = calculateMac(
    bodyWithoutMac,
    algorithm,
    key,
    macRange,
    paddingRule
)

fields[64] = mac
isoBody = encode(MTI) + encode(bitmap) + encodeFieldsInAscendingOrder(fields)

networkFrame = addChannelHeaderIfRequired(isoBody)
send(networkFrame)
```

这只是逻辑示例。部分渠道计算 MAC 时会给 MAC 域预留零值，部分渠道不把 MAC 字段本身纳入计算，必须严格遵循安全规范。

### 13.4 组包时的关键校验

- Bitmap 中置 1 的字段必须实际写入。
- 实际写入的字段必须在 Bitmap 中置 1。
- 字段顺序必须按域号升序。
- 定长字段长度必须准确。
- 变长字段的长度头必须与实际数据一致。
- 数字字段是否允许空格、符号或字母需要按定义检查。
- 金额单位和补零方向必须正确。
- Binary 数据不能被错误地当成普通字符串拼接。

## 14. 解包流程

### 14.1 网络层先获得完整报文

ISO 8583 解析器不能假设一次网络读取正好得到一条完整报文。通信层通常需要处理：

- 半包。
- 粘包。
- 超时。
- 连接断开。
- 重连和重复发送。

如果渠道有 Length 字段，应先根据 Length 获取完整帧。

### 14.2 按顺序解析

常见解包过程：

1. 解析 Length、TPDU、Header 等渠道封装，如果存在。
2. 读取 MTI。
3. 读取主位图。
4. 检查主位图 bit 1。
5. bit 1 为 1 时继续读取第二位图。
6. 按域号从小到大遍历存在的数据域。
7. 根据 FIX、LLVAR、LLLVAR 计算字段边界。
8. 根据 ASCII、BCD、Binary 等规则解码。
9. 校验字段格式和 MAC。
10. 将字段转换成业务对象并进行请求响应关联。

### 14.3 解包伪代码

```text
cursor = 0

frame = readCompleteFrame(connection)

if channelHasHeader:
    header = parseHeader(frame, cursor)
    cursor += header.length

mti = decodeMti(frame, cursor)
cursor += mtiEncodedLength

primaryBitmap = readBytes(frame, cursor, 8)
cursor += 8

if primaryBitmap.bit1 == 1:
    secondaryBitmap = readBytes(frame, cursor, 8)
    cursor += 8

presentFields = bitmapToFieldNumbers(primaryBitmap, secondaryBitmap)

for fieldNumber in presentFields ascending:
    definition = fieldDefinitions[fieldNumber]
    length = readFieldLength(frame, cursor, definition)
    valueBytes = readBytes(frame, cursor, length)
    value = decodeField(valueBytes, definition.encoding)
    validateField(value, definition)
    fields[fieldNumber] = value

verifyMacIfRequired(frame, fields)
return buildTransactionMessage(mti, fields)
```

### 14.4 解包必须做边界保护

解析网络数据时不能完全信任报文中的长度值。至少要检查：

- 长度头是否为合法数字或合法 BCD。
- 字段长度是否超过规范最大值。
- 剩余字节是否足够读取该字段。
- Bitmap 是否要求读取一个没有定义的域。
- 字段类型是否符合数字、字符或 Binary 规则。
- 数据域累计长度是否超过整条报文长度。

这些检查既是稳定性要求，也是安全要求。

## 15. 响应报文和交易状态

### 15.1 收到响应不等于业务成功

交易处理可以分成三个层次：

| 层次 | 需要判断的问题 |
|---|---|
| 通信层 | 是否完整发送和接收？是否超时或断链？ |
| 报文层 | MTI、Bitmap、字段长度和 MAC 是否正确？ |
| 业务层 | 响应码是什么？是否需要查询、冲正或对账？ |

### 15.2 请求响应关联

收到 `0210` 后，通常需要与原来的 `0200` 进行关联。常见关联信息包括：

- MTI 请求响应关系。
- DE11 系统跟踪号。
- DE37 检索参考号，如果存在。
- DE41 终端标识。
- DE42 商户或受卡方标识。
- 交易金额。
- 交易时间和日期。
- 渠道提供的其他原交易标识。

不能只看到一个 `0210` 就认为它一定属于当前等待的请求。

### 15.3 DE39 的正确理解

DE39 通常表示主机处理结果：

- `00` 在很多规范中通常表示批准或成功。
- `05` 在很多规范中通常表示拒绝或不予承兑。
- 其他码值的含义必须查具体渠道响应码表。

DE39 不是任何情况下判断交易最终状态的唯一标准。还要确认：

- 响应报文是否合法。
- 响应是否属于原请求。
- MAC 是否通过。
- 请求方是否真正收到响应。
- 是否发生超时、断链或重复发送。
- 后续查询、冲正和对账结果如何。

### 15.4 超时交易为什么危险

超时通常表示“当前系统没有在规定时间内收到结果”，不等于“对方没有处理交易”。

可能出现：

```text
终端发送 0200
        ↓
后台成功扣款
        ↓
后台发送 0210
        ↓
网络中断，终端未收到响应
```

此时终端视角是超时，发卡行视角可能已经成功。系统需要通过查询、冲正或对账使各方状态最终一致。

## 16. 常见问题与排查方法

### 16.1 服务端无响应

优先检查：

- TCP 连接是否建立。
- 请求是否真正发送出去。
- Length 是否计算正确。
- TPDU 和 Header 是否正确。
- 服务端是否在等待更多字节。
- 报文是否因格式错误被静默丢弃。
- 读取超时设置是否合理。

### 16.2 报文格式错误

优先检查：

- MTI 是否符合交易场景。
- 必选域是否完整。
- Bitmap 与实际字段是否一致。
- 字段是否按域号升序排列。
- 固定长度是否正确。
- 变长字段是否有正确长度头。

### 16.3 字段从某处开始整体错位

如果 DE41 解析异常，不要只检查 DE41。本质问题往往发生在前一个字段：

- 前一个 LLVAR/LLLVAR 长度写错。
- 长度单位理解错误。
- ASCII 长度头被当成 BCD，或者相反。
- Binary 数据被当成 HEX 字符串。
- Bitmap 多置或少置一个 bit。

排查技巧：找到“第一个出现异常的字段”，然后向前检查一个字段的结束位置。

### 16.4 金额错误

常见原因：

- 元和分转换错误。
- DE3 被误当成金额，实际金额通常是 DE4。
- 固定长度补零方向错误。
- 金额字符串中错误加入小数点。
- BCD 和 ASCII 转换错误。

### 16.5 乱码或内容异常

常见原因：

- 字段定义是 BCD，却按 ASCII 解码。
- 字段是 Binary，却直接转换为字符串。
- 中文字段字符集不一致。
- 日志把 Binary 当成 UTF-8 文本输出。
- HEX 展示值被再次进行 HEX 编码。

### 16.6 MAC 校验失败

应逐项比对：

- 双方使用的密钥是否一致。
- 密钥版本或索引是否一致。
- MAC 算法是否一致。
- 参与计算的起止范围是否一致。
- 是否包含 MTI、Bitmap、Header 或 MAC 占位值。
- 数据编码是否一致。
- 补位方式是否一致。
- MAC 结果截取方式是否一致。
- 最终传输的是原始 Binary 还是 ASCII HEX。

仅知道“双方都使用 3DES”通常不足以保证 MAC 一致。

### 16.7 排查清单

| 现象 | 第一检查点 |
|---|---|
| 无响应 | 网络、报文长度、TPDU/Header |
| 格式错误 | MTI、Bitmap、必选域、字段顺序 |
| 字段错位 | 前一个变长域的长度头 |
| 金额错误 | 单位、补零、DE4 编码 |
| 乱码 | 字段编码和字符集 |
| MAC 失败 | 密钥、算法、计算范围、补位 |
| 重复交易 | 超时重试策略、流水号、幂等处理 |

## 17. 日志和安全注意事项

支付报文可能包含卡号、PIN 数据、磁道数据和 EMV 数据。培训和调试时应遵循最小暴露原则。

### 17.1 不应直接输出的内容

- 完整真实 PAN。
- PIN Block 明文或可还原数据。
- 磁道敏感数据。
- 完整密钥和密钥分量。
- 生产 MAC 密钥。
- 其他受安全规范限制的数据。

### 17.2 推荐的日志方式

- 卡号只保留允许展示的前后部分。
- Binary 字段用 HEX 展示，但标清原始长度。
- 同时打印域号、字段长度和编码类型。
- 打印请求流水和交易关联标识。
- 不在普通日志中输出密钥和 PIN 数据。
- 区分“逻辑字段值”和“最终网络字节”。

示例：

```text
DE2  type=LLVAR encoding=BCD digits=16 value=622202******7890
DE4  type=FIX   encoding=ASCII bytes=12 value=000000001000
DE55 type=LLLVAR encoding=BINARY bytes=128 value=<omitted>
DE64 type=FIX   encoding=BINARY bytes=8 value=A1B2...0708
```

## 18. 实战练习

已知收到以下教学报文：

```text
MTI    = 0210
Bitmap = 3020040002C08001

DE3  = 000000
DE4  = 000000001000
DE11 = 123456
DE22 = 051
DE39 = 05
DE41 = SUNMI001
DE42 = 123456789012345
DE49 = 156
DE64 = 8 Bytes MAC
```

请回答：

1. 这是请求还是响应？
2. Bitmap 中有哪些数据域存在？
3. 为什么这个 Bitmap 与前面的 0200 示例不同？
4. 如果 DE41 解析错位，应优先检查什么？
5. DE39=`05` 能否脱离渠道响应码表直接下结论？
6. 收到合法的 0210 是否一定说明 POS 已经得知最终交易状态？

### 18.1 参考答案

1. `0210` 在常见实现中表示金融交易响应。
2. 存在 DE3、DE4、DE11、DE22、DE39、DE41、DE42、DE49、DE64。
3. 响应报文增加了 DE39，因此第五个 Bitmap 字节出现 `02`，最终为 `3020040002C08001`。
4. 优先检查 DE41 前面的字段，特别是变长字段的长度头、编码方式、Bitmap 和字段配置。
5. 不能。`05` 在很多规范中常表示拒绝或不予承兑，但最终含义必须查看渠道响应码表。
6. 不一定。如果响应在返回过程中丢失，后台可能已完成处理，而 POS 仍然超时。最终状态可能需要查询、冲正或对账确认。

## 19. 开发实现建议

### 19.1 使用字段定义驱动组包解包

不要为每个数据域散落大量硬编码。建议建立统一字段定义：

```text
FieldDefinition
├── fieldNumber
├── lengthType       FIX / LLVAR / LLLVAR
├── maxLength
├── lengthUnit       DIGITS / CHARS / BYTES
├── lengthEncoding   ASCII / BCD / BINARY
├── dataEncoding     ASCII / BCD / BINARY
├── alignment        LEFT / RIGHT
├── paddingCharacter
└── validator
```

这样可以让组包和解包使用同一份配置，减少两套逻辑不一致的问题。

### 19.2 将报文分层处理

建议拆分为以下模块：

```text
业务交易对象
   ↓
ISO 8583 字段映射
   ↓
字段编码 / 解码
   ↓
Bitmap 生成 / 解析
   ↓
MAC 计算 / 校验
   ↓
渠道 Header / Length
   ↓
TCP 或其他通信模块
```

避免让网络连接代码同时负责金额转换、Bitmap 生成和 MAC 计算。

### 19.3 使用测试向量

至少为以下内容准备固定测试向量：

- MTI ASCII 和 BCD 编码。
- 主位图和第二位图。
- LLVAR 偶数长度和奇数长度。
- LLLVAR 大长度字段。
- BCD 奇数位补高位、补低位和补 F。
- 金额边界值。
- 缺失必选域。
- Bitmap 与字段不一致。
- MAC 正确和错误结果。
- 报文截断和超长字段。

测试时应同时断言：

- 逻辑字段值。
- 最终 HEX 字节流。
- 解包后的字段集合。
- 组包后再解包是否保持一致。

## 21. 培训总结

需要记住的不是所有字段编号，而是下面这条主线：

```text
MTI 回答：这是什么消息？
Bitmap 回答：消息中有哪些字段？
字段定义回答：每个字段有多长、如何编码？
渠道规范回答：具体怎样封装、校验和传输？
```

实际排查报文时，可以按以下顺序思考：

1. 是否收到完整网络帧？
2. 渠道 Header 和 Length 是否正确？
3. MTI 是否符合预期？
4. Bitmap 是否与字段集合一致？
5. 字段长度头和编码是否正确？
6. 字段是否按域号升序排列？
7. MAC 是否按相同规则计算？
8. 请求响应是否正确关联？
9. DE39 和后续交易状态如何解释？

只要按照“分层、定界、编码、关联”的顺序分析，大多数 ISO 8583 报文问题都可以逐步定位。
